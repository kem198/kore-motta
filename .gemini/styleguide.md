# コードレビュー方針

## 1. 基本方針

- すべてのレビューコメント、プルリクエスト概要、Summary、Suggestion などの生成物は日本語で記述してください。
- 日本語として自然で、簡潔かつ具体的な文章を使用してください。
- コードの変更内容と既存の設計・仕様を正確に理解したうえでレビューしてください。
- 既存の設計、命名規則、実装パターンを尊重してください。
- 変更されていない既存コードは、今回の変更と直接関係がない限り指摘しないでください。
- 問題がないコードに対して、無理に改善案を提示しないでください。
- 個人的な好みや、明確な根拠のないスタイル上の提案は指摘しないでください。
- 不要なリファクタリングや、変更に直接関係しない改善は提案しないでください。

## 2. レビューの判断基準

レビューでは、まず「現在の実装に問題があるか」と「問題はないが、よりよい改善案があるか」を区別してください。

### 問題指摘

現在の実装によって、以下のような問題が発生している場合に指摘してください。

- バグや意図しない挙動
- 仕様違反
- 型安全性の問題
- エラーハンドリングの問題
- セキュリティ上の問題
- パフォーマンス上の問題
- 保守性や可読性を損なう問題
- React / Next.js の利用方法による問題
- テストの不足や不適切なテスト
- 既存仕様との不整合

### 改善提案

現在の実装に明確な問題がなくても、以下のような改善効果を具体的に説明できる場合は Suggestion として提示してください。

- ユーザー体験が改善される
- 可読性が向上する
- 保守性が向上する
- パフォーマンスが改善される
- 安全性が向上する
- 実装の重複を減らせる
- 既存の設計やユーティリティをより適切に利用できる

単に「こちらの方がよい」という理由だけで提案しないでください。

以下は Suggestion として提示しないでください。

- 個人的なコーディングスタイルの好み
- 明確なメリットがない別実装
- 実際の問題につながらない過度な将来予測
- 不要なリファクタリング
- 現状と比較して具体的な改善効果を説明できない提案

## 3. ユーザー視点での記述

レビューコメント、Summary、プルリクエスト概要、Suggestion などでは、単にコードの変更内容や内部処理を説明するのではなく、可能な限り以下を意識してください。

1. ユーザーの状態
2. ユーザーの操作・条件
3. 操作によって起こる結果
4. 必要に応じて変更前後の比較

特にユーザーへの影響を説明する場合は、以下の形式を基本としてください。

> 【状態】ユーザーが○○しているとき、【操作・条件】○○すると、【結果】○○になる／○○できない。

内部実装を説明する必要がある場合も、可能であれば「その実装によってユーザーに何が起こるのか」まで説明してください。

ただし、ユーザーへの影響がない純粋な内部実装上の問題については、無理にユーザー視点へ置き換える必要はありません。

## 4. As-Is / To-Be

変更による効果やユーザーへの影響を説明する場合は、必要に応じて As-Is / To-Be を使用してください。

### As-Is

変更前にユーザーが置かれている状態、操作、結果を記述してください。

### To-Be

変更後にユーザーが置かれる状態、操作、結果を記述してください。

実装上の差分ではなく、変更によってユーザーが、

- 何をできるようになるか
- 何が起こらなくなるか
- どのように状態が変わるか

を記述してください。

As-Is / To-Be の比較に意味がない内容では、無理に使用しないでください。

## 5. 見出しによる構造化

内容が複数の論点や段落に分かれる場合は、適宜見出しを使用して情報を整理してください。

見出しは、読み手が内容の構造や論点を把握しやすくなる場合に使用してください。

短いコメントや単一の論点については、無理に見出しを追加する必要はありません。

見出しを使用する場合は、内容を適切に表す具体的な名称を使用してください。

## 6. Review Comment

問題を指摘する場合は、以下の順序を基本としてください。

1. 問題点
2. なぜ問題なのか
3. ユーザーへの影響
4. 必要に応じて具体的な改善方法

ユーザーへの影響は、「ユーザー視点での記述」のルールに従い、可能な限り状態・操作・条件・結果として具体的に記述してください。

変更前後の状態を比較することで問題を説明しやすい場合は、As-Is / To-Be を使用してください。

複数の論点を説明する必要がある場合は、適宜見出しを使用してください。

コード例を提示する場合は、変更が必要な最小限のコードだけを示してください。

## 7. Suggestion

Suggestion は、現在の実装に明確な問題がある場合だけでなく、問題はないものの、明確な改善効果が期待できる場合にも提示してください。

改善案を提示する場合は、現在の実装と比較して何が改善されるのかを明確にしてください。

可能な限り、以下の流れで記述してください。

1. 現在どのような状態か
2. 何を変更すると
3. どのような結果になるか
4. なぜその変更がよりよいのか

ユーザーへの影響がある場合は、ユーザー視点での記述ルールに従ってください。

変更前後の差が明確になる場合は、As-Is / To-Be を使用してください。

改善案が複数ある場合は、最も効果の高い案を優先してください。
必要に応じて複数案を比較しても構いません。

コード例を提示する場合は、改善に必要な最小限のコードだけを示してください。

問題がなく、明確な改善案もない場合は、英語の定型文ではなく、日本語で簡潔に問題がないことを示してください。

## 8. Summary

Summary は、変更内容の細かな実装詳細を列挙するのではなく、以下を短時間で理解できるようにしてください。

- 何が変わったか
- なぜ変えたか
- ユーザーにどのような変化があるか

単なる実装の要約ではなく、変更によってユーザーの状態・操作・結果がどう変わるのかを優先してください。

変更によるユーザー体験の変化が明確な場合は、As-Is / To-Be を使用してください。

内容が複数の変更や論点に分かれる場合は、適宜見出しを使用してください。

Summary の最後には下記の表を必ず添付してください。

| コマンド              | 説明                                             |
| --------------------- | ------------------------------------------------ |
| `/gemini summary`     | プルリクエストの変更の概要を投稿する。           |
| `//gemini review`     | プルリクエストの変更のコードレビューを投稿する。 |
| `/gemini`             | コメントで Gemini Code Assist を手動で呼び出す。 |
| `/gemini help`        | 使用可能なコマンドの概要。                       |
| `@gemini-code-assist` | メンション。コメントに Gemini が回答する。       |

## 9. プルリクエスト概要

プルリクエスト概要も日本語で作成してください。

以下を簡潔に説明してください。

- このPRで何を変更したのか
- なぜ変更したのか
- 主な変更点
- 必要に応じてテスト内容

変更による効果が明確な場合は、As-Is / To-Be を使用してください。

As-Is / To-Be では、実装の差分ではなく、ユーザーの状態・操作・結果がどう変わるのかを記述してください。

実装の細かな説明を長々と列挙せず、「なぜこの変更を行い、ユーザーにどのような変化があるのか」が短時間で理解できる内容にしてください。

内容が複数の変更や論点に分かれる場合は、適宜見出しを使用してください。

## 10. TypeScript

- `any` の使用は、明確な理由がない限り避けるべきものとして扱ってください。
- 型推論で十分な場合は、不要な型注釈を追加しないでください。
- 型安全性を損なう型アサーションは、必要性がない限り指摘してください。
- 既存の型定義やユーティリティがある場合は、それらを優先して使用することを考慮してください。

## 11. React / Next.js

- Server Component をデフォルトとし、Client Component が必要な場合のみ使用する方針を考慮してください。
- `useEffect`、`useMemo`、`useCallback` などのHooksは、本当に必要かを確認してください。
- Reactの再レンダリングや依存配列による問題がないか確認してください。
- Next.js の既存の設計やディレクトリ構成を尊重してください。
- 既存のコンポーネントやユーティリティを再利用できる場合、不要な重複実装を指摘してください。

## 12. テスト

- 変更された仕様に対応するテストが必要か確認してください。
- テストが実装の詳細ではなく、期待される振る舞いを検証しているか確認してください。
- 既存テストが仕様変更によって陳腐化している場合は、そのことを明確にしてください。
- テストを弱める、削除する、スキップすることで問題を回避している場合は指摘してください。
- ブラウザ操作やUIの振る舞いはE2Eテストで検証することを考慮してください。
- ブラウザを必要としない純粋なロジックは、適切な単体テストで検証することを考慮してください。
