# コードレビュー方針

## 基本方針

- すべてのレビューコメントとプルリクエスト概要は日本語で記述してください。
- 日本語として自然で、簡潔かつ具体的な文章を使用してください。
- コードの変更内容を正確に理解したうえでレビューしてください。
- 変更されていない既存コードについては、今回の変更と直接関係がない限り指摘しないでください。
- 既存の設計、命名規則、実装パターンを尊重してください。
- 問題がないコードに対して、無理に改善案を提示しないでください。
- 単なる個人的な好みや、根拠のないスタイル上の提案は指摘しないでください。

## ユーザー視点での記述

コードの処理や内部実装だけでなく、その結果としてユーザーにどのような影響があるのかを可能な限り具体的に記述してください。

「○○の処理に失敗する」「○○が再実行される」のように、内部処理だけで説明せず、可能な限り以下のような具体的なシナリオで記述してください。

> 【画面・状態】ユーザーが○○しているとき、【操作・条件】ユーザーが○○すると、【結果】○○になる／ユーザーが○○できない。

### 例

悪い例：

> `useEffect` が不要に実行されることでデータが再取得される。

良い例：

> Todo一覧画面でユーザーがTodoを編集しているとき、別の操作をきっかけにTodoが再取得されると、編集中の内容が上書きされ、ユーザーが入力した内容を保存できない可能性がある。

悪い例：

> データの読み込み処理に失敗する。

良い例：

> Todo一覧画面を開いたときに保存データの読み込みに失敗すると、ユーザーが保存済みのTodoを確認できない。

悪い例：

> ボタンの状態更新が正しく行われない。

良い例：

> Todoが完了状態のときにユーザーが完了ボタンを押してもボタンの状態が変わらないため、ユーザーがTodoを未完了に戻せない。

ただし、ユーザーへの影響がない純粋な内部実装上の問題については、無理にユーザー視点へ置き換える必要はありません。

## As-Is / To-Be

コード変更による効果やユーザーへの影響を説明する場合は、可能な限り **As-Is / To-Be** の形式で変更前後を比較してください。

必要に応じて、以下の見出しを使用してください。

### As-Is

変更前の状態を、可能な限りユーザー視点で記述してください。

### To-Be

変更後の状態を、可能な限りユーザー視点で記述してください。

単に実装上の差分を説明するのではなく、変更によってユーザーの体験や利用可能な操作がどう変わるのかが分かるようにしてください。

### 例

#### As-Is

Todo一覧画面でユーザーが毎日のTodoを確認するとき、前日に完了したTodoがそのまま残っているため、ユーザーが毎日手動で未完了に戻す必要がある。

#### To-Be

Todo一覧画面を日付が変わってから開くと、Todoが自動的に未完了へ戻るため、ユーザーが毎日手動でリセットする必要がなくなる。

As-Is / To-Be の比較が意味を持たない内容については、無理にこの形式を使用する必要はありません。

## コードレビュー

レビューでは、以下の観点を確認してください。

- バグや意図しない挙動
- 型安全性
- エラーハンドリング
- パフォーマンス
- 保守性
- 可読性
- セキュリティ
- React / Next.js の適切な利用
- テストの妥当性
- 既存仕様との整合性

問題を指摘する場合は、以下を基本としてください。

1. 問題点
2. なぜ問題なのか
3. ユーザーへの影響
4. 必要に応じて具体的な改善方法

ユーザーへの影響は、「ユーザー視点での記述」のルールに従って、具体的な画面・状態・操作・結果として記述してください。

コード例を提示する場合は、変更が必要な最小限のコードだけを示してください。

## 指摘の基準

以下のような内容は、明確な問題につながらない限り指摘しないでください。

- 個人的なコーディングスタイルの好み
- 変更に直接関係しない既存コード
- 実際の問題につながらない過度な将来予測
- 不要なリファクタリング
- 単なる別実装の提案

既存コードに問題がなく、変更によって新たな問題も発生していない場合は、
「No change found to suggest.」のような英語ではなく、
日本語で簡潔に問題がないことを示してください。

## TypeScript

- `any` の使用は、明確な理由がない限り避けるべきものとして扱ってください。
- 型推論で十分な場合は、不要な型注釈を追加しないでください。
- 型安全性を損なう型アサーションは、必要性がない限り指摘してください。
- 既存の型定義やユーティリティがある場合は、それらを優先して使用することを考慮してください。

## React / Next.js

- Server Component をデフォルトとし、Client Component が必要な場合のみ使用する方針を考慮してください。
- `useEffect`、`useMemo`、`useCallback` などのHooksは、本当に必要かを確認してください。
- Reactの再レンダリングや依存配列による問題がないか確認してください。
- Next.js の既存の設計やディレクトリ構成を尊重してください。
- 既存のコンポーネントやユーティリティを再利用できる場合、不要な重複実装を指摘してください。

## テスト

- 変更された仕様に対応するテストが必要か確認してください。
- テストが実装の詳細ではなく、期待される振る舞いを検証しているか確認してください。
- 既存テストが仕様変更によって陳腐化している場合は、そのことを明確にしてください。
- テストを弱める、削除する、スキップすることで問題を回避している場合は指摘してください。
- ブラウザ操作やUIの振る舞いはE2Eテストで検証し、ブラウザを必要としない純粋なロジックは適切な単体テストで検証することを考慮してください。

## プルリクエスト概要

プルリクエスト概要も日本語で作成してください。

以下を簡潔に説明してください。

- このPRで何を変更したのか
- なぜ変更したのか
- 主な変更点
- 必要に応じてテスト内容

変更による効果が明確になる場合は、**As-Is / To-Be** の見出しを使用して変更前後を比較してください。

As-Is / To-Be では、「ユーザー視点での記述」のルールに従い、実装の差分ではなく、ユーザーの状態・操作・結果がどう変わるのかを記述してください。

実装の細かな説明を長々と列挙せず、**「なぜこの変更を行い、ユーザーにどのような変化があるのか」**が短時間で理解できるようにしてください。
