## 表記

- 日本語の文章では、全角括弧 `（）` を使用せず、半角括弧 `()` を使用する。
- 文章中の半角括弧 `()` の前後には半角スペースを入れる。
- 文章中にコードやコード要素を記載する場合は、インラインコードとして `` ` `` で囲む。
- 複数行のコードを記載する場合は、コードブロックとして ` ``` ` で囲み、使用する言語を指定する。
- 文章中に英語の単語やフレーズを記載する場合は、左右に半角スペースを入れる。
- 表記や記号は、同一プロジェクト内で統一する。

## コメント・ドキュメント

- コメントは、コードから自明な内容ではなく、理由や意図を補足するために記述する。
- 実装と矛盾するコメントを残さない。
- 不要になったコメントは削除する。
- コメントで実装の変更履歴を説明しない。
- `TODO` や `FIXME` は、必要性が明確な場合のみ使用する。

## 実装・設計

- 既存の実装・設計・抽象化を確認してから変更する。
- 既存の実装パターンを優先して使用する。
- 既存の共通処理があれば再利用する。
- 新しい抽象化は、既存の実装では対応できない場合にのみ導入する。
- 新しい依存関係は、既存の依存関係では対応できない場合にのみ追加する。
- [YAGNI 原則](https://ja.wikipedia.org/wiki/YAGNI) に従い、過度な抽象化や将来の拡張を目的とした実装を行わない。
- 型安全性を優先する。

## 命名

- 既存コードの命名規則を優先する。
- 変数名・関数名は役割が明確になる名前にする。
- 略語は一般的なものを除いて使用しない。
- Boolean 値には `is`、`has`、`can` などを使用する。
- イベントハンドラには `handle` プレフィックスを使用する。

## コードの構造

- 既存のファイル構成やディレクトリ構成を尊重する。
- 1つのファイルや関数に過剰な責務を持たせない。
- 関連する処理は適切にまとめ、責務の異なる処理を不用意に混在させない。
- 新しいファイルやディレクトリを作成する場合は、既存の構成や命名規則に従う。
